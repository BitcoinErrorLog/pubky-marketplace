# Listing drafts

Seller Studio’s create composer (`/marketplace/sell`) already autosaves a listing in progress on this device. Drop Studio does not share that form.

## Current behaviour

**Storage.** Dexie table `commerce_listing_drafts` in the `franky` database. Row id is `owner_id:listing_id`. Indexed fields: `id`, `owner_id`, `listing_id`, `updated_at`, `[owner_id+updated_at]`. Payload is `data.form` — JSON of react-hook-form values (title, description, category, price, shipping, variants, Duplicate metadata). Photos live in `useListingMediaManager` React state, not in the row. `JSON.stringify` of the form drops `File` objects, so a photo pick never reaches IndexedDB.

**Keying.** `CommerceController.getListingDrafts()` reads `getCurrentUserPubky()` and queries `owner_id`. Another identity cannot load the row. Sign-out and a real identity switch run `clearPrivateData()`, which clears every non-public table including `commerce_listing_drafts`. Same-identity flicker can skip that wipe (`shouldSkipDestructiveCleanup`). Switching A → B → A therefore does not restore A’s drafts: the table was emptied on the switch.

**Autosave.** After the first `getListingDrafts()` settles, every `useWatch` change starts a **750 ms** timer and then `commitUpdateListingDraft(draftId, formJson)`. No flush on `pagehide`, `visibilitychange`, grant/session dialog open, or failed publish. An empty form still writes (identity flicker can overwrite a contentful row with defaults). Cap: none. Newest-by-`updated_at` is `drafts[0]`.

**Restore.** On composer mount, `drafts[0]` is parsed with `createMarketplaceListingDraftSchema` and **silently** `form.reset`. The banner always reads “Draft restored / We loaded your unfinished listing from this device. Photos are not part of drafts — add them again before publishing.” plus “Discard draft and start fresh”. That banner is every composer entry with a stored row, not a choice, and not limited to a failure. Duplicate listing writes a new row and navigates to `/marketplace/sell`, which then silent-hydrates `drafts[0]` (the duplicate). Only one row is ever offered; extra rows stay in Dexie unused.

**Clear.** Successful `commitUpsertListing` deletes that draft. Failed publish, failed grant, Cancel on the session dialog, and reload do **not** call `commitDeleteListingDraft`. Discard on the banner does. Duplicate-with-replace deletes the previous unsaved id.

## Grant dialog (“The approval expired before it was completed”)

Publish without a marketplace session opens `MarketplaceSessionConnectDialog` **on top of the still-mounted composer**. The session hook maps timeout/expiry to that copy. That path does not delete the Dexie row and does not `form.reset`.

Work is lost on that path only when:

1. The last 750 ms of typing never flushed before the dialog (or a reload while the dialog was open).
2. Photos were never in the row, so a later “Draft restored” looks empty of the part that mattered.
3. `currentUserPubky` flicker plus an empty autosave overwrote the contentful row.

The failure itself does not skip or clear drafts. A later composer entry silent-hydrates whatever **was** flushed, without photos, which is easy to read as “the draft is gone.”

Playwright (vrt-marketplace, same grant overlay as staging): resume a contentful draft, publish without a marketplace session, show `The approval expired before it was completed. Try again.` The title stays in the form and `commitDeleteListingDraft` is not called. Live staging cannot drive Ring expiry without a seller session; that overlay is the same mounted-composer path.
