# Marketplace Status: What Is Real and What Is Not

Read this before evaluating the marketplace. It exists so nobody has to reverse-engineer which behavior is genuine and which is simulated.

For the complete hierarchical feature inventory, see [`FEATURES.md`](FEATURES.md).

Shop is deployed in production at <https://shop.pubky.app> (Vercel), using the production homeserver, Nexus, and Railway marketplace services. Checkout is **seller-direct**: Bitcoin binds through mainnet Paykit (`paykit-shop.pubky.app`); PayPal settles into the seller’s own PayPal account. Card payments are paused in the shop and are not offered. The marketplace never holds funds. Lightning is not a Shop checkout rail.

Last updated: 2026-09-21.

| Nexus catalog discovery                                        | The catalog is populated from the Nexus listing stream (`GET /v0/stream/listings`, implemented on the `feat/marketplace-indexing` branch of `pubky-nexus`). The index now carries the full card projection — including the auction term fields (`auction_starts_at`/`auction_ends_at`, reserve, buy-now, minimum increment, all null for fixed-price) — so the grid renders straight from validated index entries, and the canonical record is fetched from the seller's homeserver only when a listing is opened (or when the index has seen a newer revision than the cache). The homeserver stays canonical per ADR 0020. Sale format, single-condition, and the ending-soon ordering (`sorting=ends_at`) run server-side; text search, hierarchical category, price range, and the remaining sorts stay client-side. Auction cards render the seller's terms (starting bid, buy-now, end date) from the index, which cannot know bid state. In `transaction-service` mode each auction card additionally reads the durable service's public listing projection **lazily, once, when it first scrolls into view** (`useMarketplaceLiveBid`): the service exposes only per-listing reads (`GET /v1/listings/{aggregate_id}`, no batch endpoint), so the cost is one request per auction card actually seen — never N eager requests on grid render, and nothing for off-screen cards. It is a point-in-time read, not a subscription; the detail page remains the polling surface. Only when the service reports ≥1 bid does the card relabel to "Current bid" with a bid count; zero bids keeps the honest "Starting bid" label, and an unreachable service (or missing session) silently degrades back to terms-only — a bid is never invented. Sandbox mode keeps terms-only cards; its simulated bid state appears on the detail page, where it is labeled. Auction rows indexed before Nexus carried the term fields serve null terms until the operator runs the Nexus auction-terms backfill (see the deployment row below); their cards render without the end-date/buy-now badges instead of guessing. | Interactive shopping flows (durable)                           | In `transaction-service` mode the orders timeline, offers inbox, auction/bid state, cart checkout, and the post-purchase actions (ship, confirm delivery, returns, external-refund evidence, reviews) operate against the durable service: reads come from its participant-scoped projections, every command sends an `expected_revision` sourced from a freshly-read projection, and a `REVISION_CONFLICT` refetches and asks the user to retry. **Inventory rule (2026-08-24): only a payment locks an item.** Checkout creates the order without holding stock (an abandoned cart blocks nobody); stock is acquired atomically when a payment STARTS (Locks registration, fiat method bind, or staging's sandbox advance), each with a bounded server-time window (`LOCKS`/`FIAT`/`SANDBOX_PAYMENT_WINDOW_SECONDS`); an elapsed window auto-cancels the order (reason stored), restocks the unit, and routes any late-arriving money to `manual_review` — never dropped. | Encrypted messaging (durable modes)                            | **Real end-to-end encryption at experiment grade.** In `transaction-service` and `locks-paykit` modes, listing conversations run over Paykit Encrypted Links (Noise `XX_25519_ChaChaPoly_SHA256`) through the vendored browser WASM binding of the official paykit-rs messaging surface (`vendor/paykit-wasm`, provenance and checksums in [`paykit-wasm-provenance.md`](paykit-wasm-provenance.md)). The user enables messaging with its OWN Pubky Ring approval (`/pub/paykit/:rw` grant — separate from the transaction-service session); the identity secret never enters the browser, and link crypto uses a receiver-scoped Noise key generated and kept on this device. No service operator — including this marketplace's — can read message bodies; they travel and rest as ciphertext under DH-derived homeserver paths. Requirements and limits, disclosed in the UI: BOTH parties must have enabled messaging (published receiver markers) before anything can be delivered; a Noise XX handshake needs both runtimes, so nothing can be DELIVERED until the counterparty's side answers — but composing is no longer blocked pre-handshake: messages written while the handshake is pending are queued as device-local plaintext rows (`commerce_messaging_outbox`, same at-rest posture as history), labeled "Queued" in the thread and in inbox previews (`Queued: …`), cancellable while queued, validated against the same 1,000-byte ceiling at queue time, and delivered automatically IN ORDER through the real send path the moment the handshake completes (flush triggers: the conversation poll, conversation open, and the inbox sync pass; a failed flush attempt shows an honest retry note and stops the queue in place). A message is NEVER shown as sent before the binding actually sent it; one message is capped at 1,000 bytes including its envelope (live byte budget in the composer, no attachments); history (device-local plaintext by design) and the local key material (receiver Noise secret + link snapshots, encrypted AT REST with AES-GCM-256 under a non-extractable device keyring CryptoKey, each ciphertext AAD-bound to its table + row id, legacy rows wrapped in place by the idempotent DB 4 → 5 migration, writes fail closed with no plaintext fallback, and a failed best-effort boot wrap sweep is surfaced as `messagingAtRestDegraded` — the enable flow pauses with "Messaging paused: storage protection unavailable" until a later boot's sweep succeeds, since legacy plaintext rows remain at rest and readable as legacy rows in the meantime; the wrap protects against at-rest IndexedDB/disk dumps and cross-profile copying, but does NOT protect against same-origin script execution (XSS, malicious dependency), which can invoke the unwrap path — see threat-model WEB-02) live only in this browser's account-scoped IndexedDB — no other device can show the conversation; the messaging session now survives reloads, new tabs, and browser restarts (secret-free session metadata mirrored to `localStorage`; the credential itself is the browser's HTTP-only homeserver cookie, revalidated against the homeserver on restore — see `service-auth.md`, "Where the messaging session lives in the browser"), while an expired/revoked session still takes a fresh Ring approval. Proven by: real-crypto unit tests against the vendored artifact, a CI smoke gate, the binding's own 16/16 three-engine browser e2e at the pinned commit (including reload session restore), and LIVE two-party proofs driving the full client service stack — one against a local Pubky testnet (`npm run test:marketplace:messaging`) and one against the REAL staging homeserver (`ufibwbmed6jeq9k4p583go95wofakh9fwpp4k734trq79pd9u1uy`) over the public pkarr relays (`npm run test:marketplace:messaging:staging`, passed 2026-08-21 with `getTestnet() === false`, i.e. the exact client construction and topology of the staging deployment: token-gated signup, marker publish/discovery via `https://pkarr.pubky.app`, XX handshake, bidirectional chat, snapshot-restore). In both proofs only the interactive Ring approval leg is swapped for the binding's dev signup/signin helpers. Honest gaps: the live Ring-approval leg itself is unexercised, and upstream paykit-rs is pre-1.0 with no independent security review. |

## Not done, and why

### Real payments: working end to end, including the real Bitkit wallet leg (2026-08-22)

Real payments moved from deferred to **working**. The composed environment (Lock Server, Paykit Server, Bitcoin regtest, Fulcrum, pinned Pubky testnet) exists and the whole purchase path is verified live in `locks-paykit` mode — see the Real table above and [`RUNNING.md`](RUNNING.md) for how to run it and the `npm run test:marketplace:locks` suite that proves it. The Locks browser SDK is vendored and generates the canonical bundle ids; the Locks network routes stay on the verified HTTP contract for the measured reasons in the Real table. The automated suites exercise the wallet's protocol role with real tooling rather than a phone:

- **`paykit-companion-auth`** performs the `watch-only-account-v1` companion claim (Bitkit's approval role) with the seller's Pubky secret and a real bitcoind BIP84 account tpub — the same claim format the real wallet would send, without the phone.
- **`paykit-reader-demo`** receives the private Paykit Payment Request (Bitkit's protocol role) and returns the invoice's unique BIP84 address, independently re-derivable from the watch-only tpub.
- **The regtest node** executes the on-chain payment (any wallet can produce the amount-matched output; attribution is purely on-chain).

Everything protocol-side that a real wallet would talk to — invoice creation, private message delivery, address derivation, settlement observation, Locks completion, credential issuance, guarded reads, and the marketplace's independent server-side confirmation — is exercised for real. The formerly-unproven leg — the real Bitkit app UX — **was proven live on 2026-08-22**: the companion claim approved in the real Bitkit UI, the Payment Request received and rendered in the app, and the payment executed with swipe-to-pay and confirmed on-chain (proof ledger, "Bitkit wallet leg"). The phone leg stays out of the automated suites because it requires a person with a device and cannot honestly be automated. Build provenance for the vendored Locks SDK is in [`locks-sdk-provenance.md`](locks-sdk-provenance.md).

### The durable service now backs the shopping UI — with deliberate gaps

The client's `transaction-service` mode covers authenticated sessions from Pubky AuthTokens, snake_case wire, the ported command set, and the service's role-scoped read projections (listings, offers, orders with embedded payment/shipment/return/refund/review sub-objects, payments, receipts, notifications). Orders, offers, bids, checkout, and post-purchase actions operate against it: reads supply the `expected_revision` each command needs, and revision conflicts refetch and prompt a retry. What deliberately remains:

- **In-app session UX exists; the broader grant-UX question stays open.** Every durable-mode surface that needs a session now renders a "Connect marketplace session" affordance instead of a dead end: the dialog (`MarketplaceSessionConnectDialog`) states in one sentence what approval authorizes, shows the `pubkyauth://` URL as a QR for a cross-device Pubky Ring scan plus an "Open in Pubky Ring" deeplink and copy affordance (the same precedent as sign-in), waits with a cancel, and on failure shows the transport's real error with a retry that starts a FRESH flow (AuthTokens are single-use). On approval the session's public facts (never the token) mirror into the commerce store and the dependent surfaces refetch; a 401/expired session mid-action resurfaces the same affordance. What remains open in [`service-auth.md`](service-auth.md) is the product decision of whether this stays a separate approval or folds into sign-in — until then it is deliberately a second, explicit signer approval.
- **Payments in plain `transaction-service` mode stay on the sandbox adapter** — no Bitcoin in that mode, and the client refuses to send `payment.sandbox_advance` to the durable service at all, so a durable order honestly stays awaiting payment; the UI says exactly that instead of offering a simulate button. Real payments require `locks-paykit` mode, which composes with (never replaces) this mode's durable transport: the client registers the buyer's Locks correlation via `payment.register_locks` and a Locks-correlated payment advances only by the service's own verification — its Locks/paykit worker, or (for seller-direct fiat) the `/v0` fiat verification endpoints whose truth is pulled from the processor (Stripe), from PayPal's own postback-verified IPN callback (labeled gateway-notified; matched against the seller's configured email and the exact order total), or explicitly labeled seller-attested when the manual report/confirm fallback was used. No client claim ever advances one.
- **Not served by the service, not faked by the client:** notification preferences have no durable tables. Conversations/messages deliberately never got durable service tables — messaging in durable modes is end-to-end encrypted client-side (see Real), and the service never sees bodies or keys. The service-only `review.update` command now has a client contract and UI (see Real), gated to the durable mode and the 24-hour window.

So: what you click through in `transaction-service` mode is durable and authoritative; messaging is end-to-end encrypted client-side (experiment grade, labeled); and what is not available — payments in plain durable mode, notification read state/preferences — is visibly labeled as unavailable or sandbox-only.

## How to judge this work

Fair questions to ask:

- Do public records belong to the user and survive without our infrastructure? (Yes — they are on your homeserver, and now specified.)
- Does purchase HISTORY survive without our infrastructure? (Yes, for every paid order whose receipt document has published: a signed, offline-verifiable receipt sits in each participant's own `/priv` tree — see the portable-receipts row. Orders that never reached `paid`, and in-flight state like offers and bids, still die with the operator by design: the service is the authority for live transactions, the homeserver for history.)
- Are the transactional invariants actually enforced, or asserted? (Enforced by database constraints, with 100-way concurrency proofs.)
- Does the UI ever claim finality it does not have? (It should not; simulated states are labeled. Report any case that is not.)
- Could this take real money today? (Not in a normal deployment: the default mode fails closed, and `locks-paykit` refuses to activate unless every payment-rail URL is explicitly configured. The verified stack is regtest with a locally composed Lock Server and Paykit Server; nothing here has been pointed at mainnet, and doing so would first require the independent security review above.)
