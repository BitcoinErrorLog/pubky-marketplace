# Step-up approval for bridged sessions (Shop ↔ pubky.app)

**Status:** implemented (Option C) on `marketplace/pr25-ux`, 2026-09-05; reviewed and audited to SHIP. Scope: the single signer moment a user arriving via the pubky.app session bridge hits at their first commerce action. No secret, cookie, or key material appears in this document.

## Context (verified)

- The bridge (`/session-bridge`, upstream ADR 0020) replies only to allowlisted origins with the public `sessionExport` (pubky + capabilities); the credential stays an HttpOnly homeserver cookie, one per pubky, `SameSite=None` (ADR 0020 lines 16–18, 40–49; `handler.ts:13–35`). The consumer side does not yet exist in this repo (no `pubky-session`/`SessionBridge`/`vibe-session` hits under `src/`); the prototype consumer that will be ported lives outside this repo (see sketch item 3).
- Shop's homeserver grant is `CAPABILITIES = '/pub/pubky.app/:rw,/pub/paykit/:rw,/priv/pubky.app/:rw'` (`src/config/app.ts:20`); the messaging grant `PAYKIT_MESSAGING_CAPABILITY` is byte-identical because a narrower approval replaces the one cookie and broke all `/pub/pubky.app` writes (`src/libs/commerce/messaging-contracts.ts:10–23`). A bridged (narrow, `/pub/pubky.app/:rw`-only) session therefore: browses and writes `/pub/pubky.app` fine; watchlist sync degrades to `needs_reauth` (`src/core/application/commerce/commerce.ts:845–848,862`); receipt publishing silently returns (`commerce.ts:983–985`); messaging resume fails with `SessionResumeScopeMissing` and falls through to the enable prompt (`src/core/services/paykit/paykit-messaging.ts:300–327`).
- Every transaction-service action needs a bearer session from `POST /v1/auth/sessions` (`src/core/services/marketplace/marketplace-session.ts:104–182`). The token comes from `HomeserverService.generateAuthTokenFlow()` = `pubkySdk.startAuthFlow('', AuthFlowKind.signin(), relay)` + `flow.awaitToken()` (`homeserver.ts:515–541`). The service verifies raw bytes via `AuthToken::verify`, enforces a server-clock window, and records `(pubky, timestamp)` in `auth_token_uses` for single-use (`marketplace-service/crates/service/src/auth.rs:84–105,155–181`). Capabilities are extracted and stored in `auth_sessions` (`auth.rs:101,186–195`). The Paykit claim uses its own exact-scope token (`src/core/services/marketplace/marketplace-paykit-claim.ts:14,69–92`).
- **SDK fact that constrains Option A:** `pubky.d.ts` exposes `AuthFlow.awaitApproval(): Promise<Session>` (line 188) and `AuthFlow.awaitToken(): Promise<AuthToken>` (line 198) as the two terminal calls on one flow, plus `AuthToken.toBytes()/verify/fromBytes` (lines 336–366). There is **no** `signinWithAuthToken` or any public API that converts an `AuthToken` into a homeserver `Session`/cookie. One approval yields exactly one of {Session, token bytes} — never both.

## Option A — one combined approval, token reused at two verifiers

```
Shop: startAuthFlow(CAPABILITIES, signin) → QR/deeplink
Ring: ONE approval (shows full Shop grant verbatim)
Shop: token = awaitToken()
  ├─ POST token bytes → homeserver session endpoint (manual; replaces cookie with wide grant)
  └─ POST token bytes → marketplace /v1/auth/sessions → bearer session
```

- **Feasibility is the blocker.** Getting the token _bytes before_ homeserver sign-in is only possible via `awaitToken()`, but the SDK then offers no sign-in-with-token call. The homeserver cookie could only be set by re-implementing the protocol-internal session POST that `awaitApproval()` performs inside WASM (not visible in `pubky.d.ts`; exact endpoint/semantics unverifiable from the repos read). **Unverified:** whether the homeserver enforces AuthToken single-use — if it does, the same bytes cannot be accepted by both verifiers and Option A is impossible regardless.
- **Replay between verifiers:** the token is a bearer credential the service accepts only inside its 120 s window (`AUTH_TOKEN_WINDOW_SECONDS` default, `marketplace-service/crates/service/src/config.rs:93`; enforced at `auth.rs:96–98`) — tighter than the pubky-common library ceiling of 180 s (`auth.rs:44–48`), so 120 s is the effective race window. Whoever holds the bytes can, inside those 120 s, (a) race Shop to `/v1/auth/sessions` — single-use means first poster wins, and (b) if the homeserver accepts it, mint a **wide-grant cookie session in an attacker's browser**. In Options B/C the service token is empty-caps, so stealing it yields only a marketplace session, never homeserver access. This is a strictly worse blast radius for a value that transits JS memory.
- **What the service learns:** the full grant string — including `/priv/pubky.app/:rw` — is persisted in `auth_sessions.capabilities` (`auth.rs:186–195`) and returned to the client (`marketplace-session.ts:32–37`). Scope disclosure to the operator with no compensating benefit.
- **pubky.app tab after cookie replacement:** its stored `sessionExport` still lists narrow caps; `restoreSession` revalidates via the cookie (ADR 0020 line 16; `pubky.d.ts:831`). Whether it re-checks the export's capabilities against the live session is **not documented** in the SDK — uncertain; worst cases are stale reported caps (harmless: the wide grant is a superset of `/pub/pubky.app/:rw`) or a restore failure (needs an upstream fix). Must be tested empirically before shipping any option that widens the cookie.
- **Failure modes:** Ring declined → `awaitToken()` rejects (`pubky.d.ts:195–197`); nothing changed. Relay down → 120 s timeout frees the flow; dead QR by design (`marketplace-session.ts:19–27`). Service down _after_ homeserver sign-in → user holds a wide cookie but no service session; the token is re-POSTable only until the service records it — a crash between the single-use INSERT (`auth.rs:157–165`) and the response burns it and forces a **second** approval, defeating the design.

## Option B — status quo: wide homeserver re-approval + empty-caps service token

```
Bridged session (narrow) → first /priv or messaging use:
  Approval 1: startAuthFlow(CAPABILITIES) → awaitApproval() → wide cookie
First commerce action:
  Approval 2: generateAuthTokenFlow('') → awaitToken() → POST /v1/auth/sessions
```

Two Ring approvals for full functionality. Each token has one verifier, least-privilege holds (service token carries no homeserver scope), and no SDK gaps — everything uses public APIs. Costs: the user approves twice; approval 1 replaces the cookie (superset grant, so pubky.app keeps working — `messaging-contracts.ts:10–17`), and a later pubky.app sign-in reverts the cookie to narrow, requiring the degradation paths below. Failure modes are independent per approval, so partial completion always leaves a coherent state.

## Option C — defer the homeserver widening (recommended)

```
Bridged session (narrow) → first commerce action (checkout/offer/bid/…):
  ONE approval: generateAuthTokenFlow('') → awaitToken() → /v1/auth/sessions  ✅ done
Lazily, only when the user touches a scope-gated feature:
  watchlist sync → existing needs_reauth affordance → generateAuthUrl() wide re-approval
  messaging      → existing enable flow (SessionResumeScopeMissing path)
  receipts       → surfaced "paused" status instead of silent no-op → same re-approval
```

A buyer's first checkout costs **exactly one approval on every payment method** (Stripe, PayPal, BTC — see the per-method table below) with zero token reuse; seller BTC onboarding adds one one-time approval (the Paykit claim). The service session never required any homeserver capability (`homeserver.ts:522` default `''`; `auth.rs` records whatever caps arrive, empty included). The "service accepts a homeserver-cookie-backed proof" variant is infeasible: the challenge flow was removed precisely because the browser client never holds the secret key (`marketplace-service/README.md:571–579`), and the HttpOnly cookie is invisible to any third-party verifier — the AuthToken remains the only viable service credential, but nothing in the code forces the homeserver re-approval to share that moment. Graceful-degradation paths that must exist (and mostly do): watchlist `needs_reauth` UI (`commerce.ts:845–848`; `MarketplaceWatchlist.tsx:110`), messaging enable prompt (`paykit-messaging.ts:319–327`), and receipts must become visible-instead-of-silent (currently `commerce.ts:985` returns without a trace). Capability gating always reads the homeserver's own session facts (`homeserver.ts:121–141`), so a later pubky.app sign-in that reverts the cookie degrades Shop cleanly and the re-approval affordances reappear.

## Recommendation

**Option C.** It meets the "at most ONE Ring approval at first commerce action" goal using only public, shipped SDK APIs; keeps the empty-caps service token worthless against the homeserver; avoids persisting the `/priv` grant string in the service database; and reuses degradation paths that already exist. Option B is the safe fallback if product insists on widening eagerly. **Option A is rejected**: the SDK exposes no AuthToken→Session conversion (checked `pubky.d.ts`: only `awaitApproval`/`awaitToken`/`restoreSession`), it would depend on unverified homeserver single-use behaviour, and it turns the in-flight token into a wide-grant bearer credential.

## Current state of the marketplace approval (2026-09-28)

The sections above describe the service token as empty-capability. That is no longer the case. Every marketplace session request now asks for `MARKETPLACE_SESSION_GRANT` (`/pub/pubky.app/marketplace-service/v1/:rw,/priv/pubky.app/:rw`, `src/core/services/marketplace/marketplace-session-grant.ts`): the Pubky Ring "Connect marketplace" QR (a `pubkyauth://signin` AuthToken from `MarketplaceSessionService.beginSessionFlow`), the grant bootstrap, and the grant reconnect. A session that holds this grant qualifies for the `/priv` data key (`GET /v1/me/priv-keys`).

- **Authority transfer.** The Ring connect AuthToken is posted to marketplace-service. While it is fresh, the same bytes could also be posted to the homeserver `/session` endpoint and yield a session with inventory and private-data read and write. That is the same in-flight replay exposure the Ring sign-in token already has ([`single-approval.md`](single-approval.md) §5), now carried by the connect QR too. The grant flows carry no reusable token: the homeserver only honours their grant together with the flow's PoP key.
- **Disclosure.** Beside every QR or deeplink whose approval produces a session carrying marketplace capabilities, Shop shows one sentence chosen from the capabilities that request carries (`marketplaceApprovalDisclosure`, rendered by `MarketplaceApprovalDisclosure`): "Approving lets the marketplace handle your purchases and stock edits and read and write your private Shop data." for `MARKETPLACE_SESSION_GRANT`, "Approving lets the marketplace handle your purchases and stock edits." for the inventory-only grant, and "Approving signs you in to Pubky Shop and gives the marketplace the same access, including your private Shop data." for the Shop sign-in grant. No capability path, client host or signer name appears in the sentence; the signer still shows the capability string verbatim. The surfaces:
  - `MarketplaceSessionConnectDialog` in every mode: the Ring connect QR and its "Open in Pubky Ring" link, the grant bootstrap QR and link, the grant reconnect QR and link, and the bridged full-grant connect QR.
  - The Ring sign-in QR and the Ring "Authorize" deeplink button, in both the Ring-only and the Ring-plus-Bitkit layouts (`SignIn`, `SignerAuthOption`), and the Ring step-up QR and link (`MarketplaceReauthDialog`). These carry the sign-in sentence only when `signInApprovalDisclosure` holds: single approval is on and the commerce mode is durable, the two conditions under which `AuthApplication.completeSingleApprovalCeremony` also redeems the token at the marketplace.
  - The Inventory Studio grant QR and link (`MarketplaceInventoryGrantDialog`), whose AuthToken mints a marketplace inventory session.
  - Not disclosed, because they produce no session with marketplace capabilities: the Bitkit sign-in and sign-up grant QRs (the grant session is never redeemed at the marketplace), the Ring sign-up QR and the Ring sign-in without single approval (cookie flows), the messaging enable QR (Paykit), and the Lock Server connect (a Lock Server session).
- **Session replacement.** Every path that puts a purchase session into memory or storage runs `MarketplaceSessionService.replacementRejection` first (`sessionReplacementRejection`): exact grant match (any order, no blank or duplicate entry) and no loss of inventory or private-data coverage that the current session for the same pubky holds.
  - `establishWithAuthToken` from the Ring connect QR accepts only `MARKETPLACE_SESSION_GRANT`; from the sign-in redeem (Ring sign-in, Ring step-up, bridged connect, and the already-used retry) only `CAPABILITIES`. It writes memory and `localStorage`.
  - `establishClaimedGrantSession` (grant bootstrap, grant reconnect) accepts only one of the two marketplace session grants. It writes memory and `localStorage`.
  - `restorePersistedSession` reads `localStorage` on page-load hydration (`AuthController.restorePersistedSession`), on Seller Studio submission and own-drop loads (`CommerceController.restorePersistedMarketplaceSession`), and inside the already-used redeem. It accepts the grants a writer may have stored (either marketplace session grant or `CAPABILITIES`); anything else, including the empty-capability sessions older releases stored, is dropped from storage. Because `localStorage` is shared across tabs, a narrower blob for the same pubky never replaces a wider in-memory session: the restore keeps memory, leaves the other tab's blob alone, and returns the in-memory facts.
  - The commerce store mirror (`CommerceController.writeMarketplaceSessionStore`) only ever receives what those three return. Nothing else writes the session: there is no IndexedDB copy, no cross-tab listener for this key (the auth `BroadcastChannel` carries only sign-out, which clears the session), and no migration of older keys.

  A refused establish is never stored; the current session stays and the dialog shows why.

- **Clearing and overwriting the persisted session.** `localStorage` and the BFF session cookie are shared across tabs, so another tab may hold a newer bearer there. Every path that removes or overwrites the record touches only what it owns:
  - `clearSession` (TTL margin in `getActiveSession`, revocation in Inventory automations, checkout hold expiry, a losing or failed sign-in, a step-up for another identity) removes the persisted record only when it still carries the in-memory bearer, and asks the BFF to unpair only that session's `session_id` (`DELETE /api/marketplace/session?session_id=…`, which deletes the bridge only while it pairs that session and keeps the shared cookie otherwise). With nothing in memory it removes nothing.
  - A 401 (`MarketplaceTransactionService`, Inventory Studio's purchase bearer) and a session minted for another pubky clear through `clearSessionIfBearer`, only while the bearer the request carried is still the in-memory one.
  - `restorePersistedSession` expires memory before reading the slot, and removes a malformed, expired or unexpected record only while the slot still holds exactly the record it read. Another account's record is not the caller's: restore leaves it, and sign-out or account switch removes it.
  - `writePersistedSession` (both establish writers) does not overwrite a different bearer that expires later: another tab minted after this tab's request left.
  - Sign-out (`AuthController` local-state cleanup) calls `clearForSignOut`, the one path that removes a record it did not write and unpairs the cookie unscoped, because no purchase bearer may stay at rest for the user who is leaving.
  - A sign-in that replaces another account without a sign-out (`AuthController.persistIdentityUnderLock`) calls `clearOtherAccounts(newPubky)`: every record and in-memory session of another account goes, its BFF pairing is unpaired by its own `session_id`, and a bearer the new account already minted stays and is persisted again if the departed record had kept it out.

- **The same rule for every other persisted session.** Each slot has one identity check before any clear or overwrite, and only sign-out wipes unconditionally:

## Re-approval routing for Bitkit and Pubky Ring sign-ins

A Bitkit sign-in (`pubkyauth://signin_grant`) requests exactly `CAPABILITIES`, and the Shop refuses anything else: `AuthApplication.assertFullGrantSession` signs out and rejects an approved grant session whose `info.capabilities` do not match `capabilitiesMatchFullGrant`, and a stored grant session that restores narrower is signed out and its record removed. Every live grant session therefore already holds `/priv/pubky.app/:rw`, so `canCurrentSessionWrite(PRIVATE_APP_DATA_PATH)` is true and the homeserver-capability `needs_reauth` state cannot occur for it.

`MarketplaceReauthDialog` takes the refusal's source (`refusal`) and routes on it, never on session facts:

- **Homeserver refusal** (`refusal="homeserver"`): the watchlist and receipts `needs_reauth` states, raised when the Shop session's grant cannot write `/priv/pubky.app/` or the private document answers 401/403. A cookie sign-in gets the Pubky Ring step-up, the only approval that repairs it. None of these fires for a Bitkit sign-in; if one did, the Bitkit sign-in, which cannot run the Ring step-up, gets `MarketplaceSessionConnectDialog`.
- **Purchase-session refusal** (`refusal="purchase_session"`): the marketplace would not release the private data key (`GET /v1/me/priv-keys` 403 `needs_reauth`, or no purchase session for the owner, `CommercePrivKeyringApplication.get`). Watchlist sync and receipt publication report `needs_marketplace_approval`; the recovery-key export reports `needs_reauth`. Only a marketplace session approval that includes `/priv/pubky.app/` repairs it, so every signer gets `MarketplaceSessionConnectDialog`: with the grant flow on, the grant reconnect (Bitkit or Pubky Ring) when a purchase session exists and the grant bootstrap otherwise, for every sign-in (#49); with it off, the Ring connect QR for a Pubky Ring sign-in. The watchlist ("Approve private sync"), the order receipt line ("Approve private storage") and Settings → Marketplace data ("Approve private data") open it.

The replacement guard accepts the reconnect: an inventory-only purchase session replaced by one with `MARKETPLACE_SESSION_GRANT` for the same pubky gains private-data coverage and loses nothing. The reverse is refused as narrower.

`MarketplaceWatchlist.keyRelease.journey.test.tsx` proves the Bitkit journey with nothing in the Shop mocked: the real watchlist template and its hooks, keyring holder, purchase-session service, grant and bootstrap clients, Dexie and stores, with only `fetch` (service and BFF wire bodies) and the homeserver transport stubbed. It covers a Bitkit sign-in with an inventory-only purchase session (grant reconnect) and with none (Bitkit bootstrap): the key release is refused, the watchlist shows the approval, Bitkit approves, the purchase session is replaced, and the next sync gets the key and seals the watchlist. `MarketplaceBitkitApproval.journey.test.tsx` covers the homeserver routing with the dialog mounted directly.

The Bitkit re-approval journeys that are reachable on this release are the durable surfaces' `MarketplaceSessionRequiredCard`, which offers the Bitkit bootstrap to a Bitkit sign-in with no purchase session, and Inventory Studio, whose grant dialog re-approves the purchase session for a Bitkit sign-in. Both mint a purchase session with the full marketplace session grant. A live staging check (2026-09-28, homegate `ip_verification` accounts, Paykit rc55's Bitkit approval path) approved that grant while an inventory-only grant for the same client stayed live.

### Purchase approval is always a grant link (#49)

With `marketplaceGrantFlowEnabled` on, `useMarketplaceSessionConnect.start()` gives every signed-in user a `pubkyauth://signin_grant` link carrying exactly `MARKETPLACE_SESSION_GRANT`, which Pubky Ring 2.0 or later, or Bitkit, approves. Ring 2.0 is on Android only so far; iOS Ring users run 1.19, which signs in (and, with single approval, gets a purchase session at sign-in) but cannot approve this link. Bitkit rejects the Ring connect AuthToken link (`pubkyauth://signin`), so no signed-in path falls back to it:

| Shop session                                | Purchase session | Approval                                                                                                                  |
| ------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------- |
| any (Bitkit or Passport grant, Ring cookie) | none             | grant bootstrap for the session's pubky                                                                                   |
| any                                         | active           | grant reconnect; when the BFF has no paired cookie (`shop_session_missing` / `shop_session_expired`), the grant bootstrap |
| Passport, reconnect needs a session         | active           | failure copy (the bootstrap popup needs a fresh click)                                                                    |
| none, or grant flow off                     | —                | Ring connect AuthToken (grant sessions are refused with the flow off)                                                     |

The bootstrap does not depend on the Shop session type: the browser writes the single-use proof document with whichever homeserver session it holds (a Ring cookie session has `/pub/pubky.app/:rw`), and the BFF reads it back over public HTTP. A Ring sign-in names "Pubky Ring or Bitkit" as the approving signer, since either may hold its pubky. When a grant approval lapses unapproved, the dialog adds `GRANT_APPROVAL_SIGNER_HINT`: a signer that cannot parse the link (Bitkit with a legacy link, Pubky Ring before 2.0 with a grant link) never answers, so the Shop sees only the expiry. Claimed bootstrap sessions carry no `session_id`, so the BFF is not paired for them, and a later reconnect for such a session falls back to a fresh bootstrap approval.

The other `needs_reauth` trigger is a 401/403 on the private document. For a grant session with the full grant, that refusal means the grant itself is no longer honored (revoked in Bitkit, or expired). A step-up approval widens scope; it cannot repair a refused grant. `CommerceApplication.isPrivateAccessDenied` therefore does not report `needs_reauth` for a grant session: watchlist sync reports `error` (the outbox job stays pending) and receipt publication reports `unavailable`, both retried on the next load.

`AuthController.getStepUpAuthUrl` still refuses a grant session before any Ring flow starts, so a path that reaches the homeserver step-up with a grant session gets an error in the dialog, not a Ring step-up that would replace the grant session with a cookie session while its grant record stays stored.
