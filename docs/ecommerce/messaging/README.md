# Marketplace Private Messaging — Encrypted Transport Research (plan task 5.1)

Date: 2026-08-20. Research-first evaluation; **no product code was implemented** — the decisive choice is an architecture/product decision that is not the implementer's to make. This repo contains the evaluation, the recommendation, and a handoff-ready plan.

> **Update, 2026-09-05 (latest) — key material is now encrypted at rest.** The receiver Noise secret (`commerce_messaging_receivers.noise_secret`) and Encrypted Link snapshots (`commerce_messaging_links.snapshot`) are no longer stored as plaintext in IndexedDB. Each is wrapped with AES-GCM-256 under a single NON-EXTRACTABLE CryptoKey generated on first use and persisted in a dedicated tiny IndexedDB database (`<db>-messaging-keyring`; `src/libs/crypto/messaging-keyring.ts` — the WebKeyStore design proven by the sibling Hypercolor web app, adapted to this repo's layering). Every ciphertext carries a fresh 96-bit IV and AAD of `pubky-app.messaging-wrap.v1|<table>|<rowId>`, so a ciphertext transplanted into another row or table fails GCM authentication instead of decrypting. Rows carry `wrap_version`, tri-state on read: 1 = wrapped (unwrapped on read); absent/0 = legacy plaintext (tolerated until the migration wraps the row); ANY OTHER value (corrupted or future format) = LOST, exactly like an authentication failure — the row's bytes are never served to the Noise binding as plaintext key material. DB version 4 → 5 bumps with an UNCHANGED Dexie schema and an idempotent in-place migration that wraps legacy rows on upgrade (a versions-match sweep on every boot heals a crash-interrupted pass) instead of the usual delete-and-recreate — the rows being wrapped ARE the user's messaging identity, so wiping them would orphan every link. Failure posture, fail closed everywhere: no WebCrypto or no IndexedDB means wrapping/unwrapping throws via the `Err.database` taxonomy and writes NEVER fall back to plaintext; a ciphertext that fails authentication (lost wrapping key, tampered/transplanted row) reads as LOST — the receiver/link is treated as absent and the existing re-enable/re-handshake affordances recover. Message history and the queued outbox are wrapped the same way (see "Messaging keys and history at rest" below); everything stays on this one device (the multi-device backup-key decision is still deliberately unmade), and nothing syncs, exports, or logs. Reads unwrap inside `LocalMessagingService`, so no layer above it sees the wrapping. Residual-risk disclosure: the versions-match sweep on every boot is BEST-EFFORT by design (a failure must not brick the whole app for a messaging-only problem — the 4 → 5 upgrade-path failure stays fatal), so a persistently failing sweep leaves legacy plaintext rows at rest AND still served on read as legacy rows. That failure is no longer silent: initialization reports it as `messagingAtRestDegraded` (`DatabaseInitResult`), the fact is mirrored into the messaging store, and the enable flow pauses with "Messaging paused: storage protection unavailable" until a later boot's sweep succeeds and wraps the rows. Wrapping-key creation is race-proof: the whole load-or-create is single-flighted per tab, the read + write run as get-then-`add` inside ONE `readwrite` transaction (a `ConstraintError` adopts the other tab's stored key rather than overwriting it), and the create path takes a Web Locks named lock when the platform offers one. Proven by unit tests for the wrap/unwrap round-trip, IV uniqueness, AAD binding, idempotent migration of plaintext rows, fail-closed paths, lost-key/tamper recovery, unknown-`wrap_version` rows reading as lost, single-flighted concurrent key creation and cross-tab create-race adoption, and the degraded-sweep reporting path, plus the full pre-existing messaging suites running unchanged against wrapped storage.

## Findings in one paragraph

Paykit Encrypted Links (official `pubky/paykit-rs`, riding official `pubky/pubky-noise`) are the only reviewed encrypted transport this ecosystem provides, and — contrary to first appearance — the no-browser-identity-key constraint does **not** block them: the link crypto uses a random receiver-scoped Noise key (`ReceiverNoiseSecretKey::random()`), never the identity secret, and the homeserver session it needs comes from a Ring-approved grant. Generic marketplace message kinds are in-contract via the public `send_private_application_message_json` API. What the constraint _does_ decide is where the Paykit Rust runtime and the receiver key live, and that is the fork: a marketplace-run Rust adapter ships sooner but **its operator can decrypt messages** (relocating, not fixing, the problem the task exists to fix), while a browser WASM binding of paykit/pubky-noise actually fixes it but requires upstream packaging work that doesn't exist yet (verified: no wasm CI or binding; out-of-the-box wasm32 build fails on getrandom backend config and ring's C toolchain — packaging obstacles, not API blockers). Direct pubky-noise use collapses into Paykit (using it raw means re-designing the protocol layer Paykit already reviewed); homeserver-encrypted-records collapses too (no counterparty-readable private paths exist, so every honest instantiation reinvents pubky-noise, which is forbidden hand-rolled protocol design); the legacy `/Volumes/vibedrive` forks of both repos are self-declared deprecated, non-interoperable with the official libraries, and disqualified.

## Recommendation and confidence

**Adopt Paykit Encrypted Links as the transport. Target the browser-WASM topology as the end state; do not build the server-side adapter unless the product owner explicitly accepts and labels its operator-can-decrypt property.**

- That Paykit-over-pubky-noise is the only viable ecosystem candidate: **high confidence** (all alternatives are blocked by verified, specific facts).
- That the no-identity-key constraint is compatible with Paykit: **high confidence** (verified in source, not docs: `handshake.rs:127`, `identity.rs:210/267`, `paths.rs`).
- That the browser WASM binding is achievable upstream: **medium confidence** (dependency stack already ships a browser build as `@synonymdev/pubky`; the two observed build failures are packaging-class; but nobody has done it, there is no wasm CI, and effort/timeline belong to upstream).
- That the adapter topology would be acceptable: **low confidence, and it is not mine to accept** — it fails the stated goal ("readable by its operator" is the thing being fixed) and is defensible only as an explicitly-labelled intermediate step.

## Decisions a human must make

1. **Topology** (the gating decision): (a) marketplace-run Rust messaging adapter — sooner, operator can decrypt, must be labelled as such; (b) upstream browser WASM binding — actually operator-unreadable, timeline owned by upstream; (c) keep messaging sandbox-only until (b) or a user-side Paykit runtime (e.g. Bitkit companion) exists. My recommendation: (b), with (c) as the honest meantime; build (a) only as a consciously labelled intermediate.
2. **Multi-device backup key** (topology b): what encrypts the `SdkBackupState`/snapshot blob — user passphrase, recovery-file-derived key, or a Ring-mediated wrap? Paykit deliberately leaves this to the caller. Determines whether a second device / re-login recovers history or starts fresh.
3. **Ring grant UX**: messaging needs a homeserver grant covering `/pub/paykit/…`, beyond the app's `/pub/pubky.app/:rw`. Separate approval or folded in — the same open product decision family as `service-auth.md`.
4. **Upstream engagement**: whether to file/fund the wasm-binding and message-kind-namespace work on `pubky/paykit-rs` / `pubky/pubky-noise` (issues drafted as plan Phase 0.3).

## First contact, Requests and mutes

The transport cannot list inbound handshakes, so a seller finds a new buyer through two public records the buyer writes on the first message in a listing thread:

- a follow of the seller (`/pub/pubky.app/follows/{seller}`), which puts the buyer in the seller's followers; the dialog says so above Send: "Sending also follows this shop so they can see your message.";
- a conversation request, one per listing, with no message in it:

```
pubky://{buyer}/pub/pubky.app/marketplace/v1/conversation-requests/{seller}/{listingId}

{ "version": 1, "kind": "marketplace.conversation_request.v0",
  "seller_pubky": "<seller>", "buyer_pubky": "<buyer>",
  "listing_id": "<listingId>", "created_at": <buyer clock, Unix ms> }
```

Like the other `marketplace/v1/*` paths, this is a Shop convention and not part of `pubky-app-specs`. The record is public: anyone can read which seller and listing a buyer asked about. The buyer reads it first and writes it only when it is missing or invalid; a failed read writes nothing. Both sides of an order or offer already find each other, so a first message about one writes neither record.

On each inbox sync the seller lists the request directory of up to 20 followers and adds one listing thread per valid request. Only the path is trusted: the homeserver lets nobody but the buyer write under the buyer's `/pub`, and every JSON field must repeat the path or the request is ignored. Messages are then accepted into a thread only when its id names both authenticated ends of the link.

A thread with someone the account does not follow, shares no order or offer with, and has never written to lands in **Requests**. Requests never count as unread. Accept, a reply, a follow of the person or a shared order moves every thread with them into the inbox.

Mutes are private and kept as an add-only log under `/priv/pubky.app/marketplace/v2/s/`, family `messaging_mutes`, sealed with the same data keys and envelope as the watchlist (see `docs/ecommerce/priv-encryption-recovery.md`). Each mute or unmute is its own record under a fresh random name and is never rewritten or deleted, so two devices, two tabs or a reload in the middle of a change never lose one another's changes; per person the latest change wins and a mute wins a tie. A muted person is never probed, sent to or stored, and their threads are hidden. At most 1,000 people can be muted at once. A list saved in the earlier single-document format (entry id `mutes`) is still read and folded in, so none of its mutes is lost; if it does not open, the list cannot be confirmed.

Every operation that contacts someone (opening or advancing a link, sending, flushing queued messages, receiving, reading request directories) first reads the whole log. If any part of it cannot be read or opened, nothing contacts anyone, nothing new is stored, and nothing about any conversation is shown: the inbox, Requests and Messages list no rows or previews, conversation history and queued messages are not returned, the unread badge shows nothing, and conversations say that new messages are paused. Surfaces that show message content read the list themselves each time. A list read earlier never stands in for a failed read. In durable modes no marketplace notification of a message is shown at all (no service writer exists; the inbox is the only surface for private messages). Messages wait on the homeserver until the list reads again. Messages a muted person sent arrive after an unmute.

Events of a kind or version this build cannot interpret (for example Paykit payment kinds on the same link, or a newer chat version) are stored before the link's read position moves past them, encrypted at rest in `commerce_messaging_unprocessed` (kind and version included, so nothing about the event is stored in the clear), never shown, and offered to the router again on every later receive. If storing anything from a batch fails, the live link handle, whose read position already moved past the batch, is dropped, so the next receive restores it from the last persisted snapshot and reads the batch again. That table needs `NEXT_PUBLIC_DB_VERSION=8`; with an older version, a link that receives such an event stops there instead of reading past it.

A link's send counter is never used twice. Before a message leaves, the link row is marked as sending; the snapshot saved after the send, whether it succeeded or failed, clears the mark. If that snapshot cannot be saved, the pair keeps its live handle and saves the snapshot before its next send or receive, and does neither until the save succeeds. A handle whose failed receive is dropped is only that handle, never one a later sign-in put under the same pair. A link found still marked after a reload may have sent past its saved snapshot, so it is never restored from it: it reports `recovery-needed` (`send-state-unknown`), keeps its row and queued messages, and sends nothing. A completed handshake, and an adopted inbound link, are used only after they are saved; a completed handshake that cannot be saved restarts from its saved handshake state.

Every tab restores its own handle from the same saved snapshot, so every operation on a link (sending a chat message or DM, flushing queued messages and their retries, receiving, and every handshake step, probe and restore) holds a Web Lock named `pubky-messaging-link|<owner>|<counterparty>`, shared by every tab of the origin. Holding it, a tab compares the link row with the revision it last wrote or read (a random `write_id` replaced by every write, plus the stored snapshot, which is re-wrapped under a fresh IV on every save). If another tab has written the row since then, the tab drops its in-memory handle or handshake and continues from the saved state, so it never sends under a counter another tab already used, completes a handshake another tab already completed, or saves a snapshot behind another tab's send. Without the Web Locks API, or when the browser refuses the lock, nothing on the link runs: sends, receives and handshake steps fail with "Private messages are paused", and queued messages stay queued. Setting up the account's receiver (reading, creating or replacing its Noise key, publishing its marker and marking it published) holds a second Web Lock, `pubky-messaging-receiver|<owner>`, on every path that reaches it: enabling, restoring the session after a reload, resuming from the sign-in cookie, and the restore a link operation runs when the tab has no session. The receiver is read only once that lock is held, a new key is stored only if no receiver exists (one some other writer stored meanwhile is adopted), and the row is marked published only while it still holds the key that was published, so every tab ends with one key and the marker advertises it. A link never uses a receiver whose marker is not published yet. Without Web Locks, nothing is set up. A link operation can provision the receiver while holding its pair lock, so the receiver lock comes after the pair lock; nothing holding the receiver lock takes a pair lock or the receiver lock again. The keyring's wrapping key is read and added in one IndexedDB transaction that adopts a key another tab added first. Every read and write of key-wrapped state (receiver, link and kept-event rows, and the boot wrap sweep) holds a third Web Lock, `pubky-messaging-keys`, in shared mode, only around the database work itself and never across a network call; sign-out and identity cleanup take it exclusively. Holding it, a tab checks that the key it cached is still the persisted one: the epoch it cached with the key must equal the epoch stored next to the key in the keyring. The epoch is a random id written in the same transaction as the key record and replaced whenever a new key record is stored (created, or healed after the stored one became unusable), and it disappears with the keyring, including when a tab of an older build signs out without the lock. If the epochs differ, nothing is read or written, the cached key is dropped, and the tab ends its messaging session, so no tab writes state under a key that was cleared or replaced, or mistakes rows it can no longer open for corrupt ones and replaces them. Sign-out clears the other tables at once, sets a pending flag in `localStorage`, then deletes the key and clears the receiver, link and kept-event rows only once it holds the fence exclusively, so it never runs while any tab is part-way through a fenced read or write, however long that tab is suspended. While the flag is set every fenced operation refuses. Sign-out returns after 10 seconds with the teardown still queued; if the tab closes first, the next load finishes it. Each tab's keyring connection closes as soon as another tab deletes the keyring, so a deletion never waits on an open tab. Full lock order: pair lock, then receiver lock, then the key fence, then the keyring's create lock; the key fence is held only around one database operation and never taken twice by one call, and sign-out holds only the key fence. The persisted session metadata holds no key material; two tabs writing it both write a valid session. The boot wrap sweep of legacy plaintext receiver and link rows replaces a row only if it still holds the key or snapshot the sweep wrapped. A tab still running a build from before this lock neither takes it nor writes `write_id`, so the protection holds once every open tab runs this build.

Accounts signed in through a Bitkit grant cannot turn on private messages yet; they see the Ring-only notice, and none of the above applies to them until the messaging runtime can borrow their session.

Limits, on this device's clock (never a sender's `sent_at`): a buyer can message at most 5 new people per rolling hour, and at most 20 messages per minute from one person are stored. Both are counted from IndexedDB, so another tab or a reload does not reset them, and the new-people check and its record are one transaction, so concurrent sends cannot all pass it. Both bind honest clients only; mute, Requests and the probe budget (10 of the 25 probes per sync kept for people with no local state) are the defences that hold against a modified client. Report copies the conversation id and the other account to the clipboard and builds no URL.

This policy sits above the transport behind `MessagingIntakeGate` (`src/libs/messaging/intake-gate.ts`): the link runtime asks it once per inbound message before storing it.

## Messaging keys and history at rest

Each account publishes one receiver marker, `/pub/paykit/v0/marketplace/wallet/receiver.json`, advertising this device's receiver Noise key. The marker is unsigned: any app whose grant covers `/pub/paykit/`, or another device of the same account, can overwrite it.

**This device's marker.** Once per messaging session, after the session resumes, the Shop reads the marker it publishes and compares its key with the receiver key this device holds. The check holds the account's receiver lock, so no tab of this device publishes in between. If the marker advertises another key, or none, the Shop publishes this device's key again and tells the user once ("Another app or device replaced your private-messaging key…" or "…was missing from your account…"). A marker that cannot be read publishes nothing and is checked again on the messaging retry schedule. Two devices of one account that each republish on load will keep replacing each other's key, and each load says so; one active messaging device per account remains the model.

**Each contact's key (trust on first use).** The counterparty key of the first link with a person, recorded on the link row (`commerce_messaging_links.remote_noise_public_key`, keyed `<owner>:<counterparty>`), is that person's pinned key. It is checked:

- before any new handshake starts or an inbound one is answered, including for a link row whose snapshot no longer opens;
- after a pending handshake is advanced (a handshake already bound to the pinned key may still complete);
- when an established link is restored, by reading the person's marker once per restore;
- against the key the binding reports for every restored, completed or answered link (`EncryptedLinkHandle.remoteNoisePublicKey()`); a different one is refused as `recovery-needed` (`link-key-mismatch`) and the link is closed unsaved.

When the marker advertises a different key, the pair is held as `key-changed`: the new key is recorded on the row (`observed_noise_public_key`), no handshake starts with it, nothing is sent, and messages written meanwhile stay queued on this device. An established link on the pinned key keeps receiving, so messages the person sent before the change still arrive. The marker is read again on the retry schedule; if it advertises the pinned key again, the hold clears by itself. The conversation shows "This contact's messaging key changed" with two actions:

- **Verify key** shows the new and the previous key in groups of four characters, and asks the user to compare the new key, through a channel they already trust, with the key the other person sees under **Messaging keys** in the same conversation on their device. **Messaging keys** (in every conversation's options) shows this device's key and the key pinned for the other person.
- **Accept new key** accepts only the key recorded as shown to the user, and only while the marker still advertises it. Any other key is refused; a marker that moved on to another key records that key as shown and asks again, accepting nothing. Messages still waiting on the old link are received first; then the pair's old link state is replaced by a fresh handshake on the accepted key, which becomes the pinned key, and queued messages are sent once that link is ready.

What this does not cover: the static key a peer actually uses inside the Noise handshake. The vendored binding does not expose it; `remoteNoisePublicKey()` returns the marker key the link was created with. The pin binds a link to the marker key its message paths are derived from, so a link only works with whoever holds that key's secret, but a first contact still trusts whatever marker is published at that moment.

**History at rest.** Message bodies in `commerce_messaging_messages` and `commerce_messaging_outbox` are encrypted like the receiver secret and link snapshots: AES-GCM-256 under the non-extractable keyring key, AAD `pubky-app.messaging-wrap.v1|<table>|<rowId>`, stored in `sealed_body` with `wrap_version` 1 and an empty stored `body`. Reads unwrap inside `LocalMessagingService`; a body that does not open, or a row with an unknown wrap format, is treated as lost and not shown. Writes fail closed without the key fence. Plaintext rows written by earlier builds are sealed in place by a sweep on every boot and on every in-place version upgrade (no Dexie version change: the new fields are not indexed). A row another tab rewrote during the sweep is left to that write and sealed by the next sweep. A failed sweep leaves those rows readable, reports `messagingAtRestDegraded`, and is retried on the next boot. While a tab of an older build is still open it keeps writing plaintext bodies, so the sweep also runs on a messaging status read, at most once every five minutes per tab. That older tab shows sealed messages as empty bubbles and its queued sends stop at the first sealed row (it never sends an empty body) until it reloads. Conversation rows (who, which listing, timestamps) stay in the clear, as do the counts and checkpoints derived from them. Sign-out clears the history and outbox tables together with the wrapping key.
